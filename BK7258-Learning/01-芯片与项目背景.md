# 芯片与项目背景

> 这一篇回答一个最根本的问题：**BK7258 到底是什么芯片，我们为什么要为它写一套 open-vela / NuttX 系统。**
> 读完你会对"芯片规格 → 三核架构 → 软件栈 → 仓库布局"有一条清晰的主线。

---

## 模块一：BK7258 芯片是什么

### 【理论】

BK7258 是 **博通集成（Beken）** 出品的一颗 **Wi-Fi 6 + BLE 5.4 Combo SoC**（SoC = System on Chip，片上系统，就是把 CPU、内存控制器、无线射频、各种外设都集成到一颗芯片里）。

它在产品上以**模组**形态出现——也就是一块已经把芯片、晶振、天线等焊好的"小电路板"。本项目用的模组是 **涂鸦 T5-AI 系列**：**T5AI-Core V1.0.1** 是兼容性默认，当前板级验证主要在 **T5-Board** 上进行。可以把它理解成：芯片是"发动机"，模组是把发动机装好、接好油管水箱的"整车"，我们拿整车来开发。

通俗地说：这颗芯片既能连高速 Wi-Fi，又能跑低功耗蓝牙，还内置了 3 个 CPU 核和一堆外设接口，是做"带联网能力的智能硬件"的好底子。

### 【图解】

```
            ┌─────────────────────────────────────────┐
            │            BK7258 SoC (单芯片)            │
            │                                           │
            │   CPU0(M33)   CPU1(M33)   CPU2(M33)       │
            │   [控制面 CP]   [应用面 AP]  [应用面 AP]   │
            │       │            │            │         │
            │   ┌───┴────────────┴────────────┴───┐     │
            │   │      共享总线 / 片上互联          │     │
            │   └───┬────────────┬────────────┬───┘     │
            │    Wi-Fi6     BLE5.4    GPIO/UART/        │
            │   射频       射频       I2C/SPI/PWM...     │
            └────┬───────────┬───────────┬─────────────┘
                 │           │           │
            Flash(8MiB)  PSRAM(16MiB)  调试口 SWD
            (模组内置)    (模组内置SiP)  (P0/P1 已验证)

   模组形态：涂鸦 T5-AI  (T5AI-Core V1.0.1)  = 上面这颗 SoC + 外围件
```

### 【实操步骤】

1. 在仓库文档目录找到硬件资料，确认模组型号：
   ```bash
   ls /home/lijian/project/open-vela/contest2026_135_yongwangzhiqian/docs/bk7258-t5ai/hardware/
   ```
2. 打开 `t5ai-core-v101-hardware-map.md` 看模组引脚与接口分布图。
3. 记住一句话结论：**BK7258 = Beken 的 Wi-Fi6+BLE5.4 三核 SoC；本项目实物是涂鸦 T5-AI 模组。**

### 【背景知识】

> 💡 **什么是 SoC / 模组？** 普通电脑的 CPU、内存、网卡是分开的零件；而嵌入式芯片往往把这些都塞进"一颗芯片"（SoC）。但单颗芯片不好直接焊到产品上，厂家就把它再焊到一块小板子上、配好天线和晶振，做成"模组"卖给你——你只要把模组当成一个"现成的联网大脑"用就行。

## 模块二：三核架构（CP / AP）

### 【理论】

BK7258 里有 **3 个 ARM Cortex-M33 内核**（型号 STAR r1p0）。它不是一个核，而是三个"工人"，各管一摊：

- **CPU0 = CP（Control Plane，控制面）**：跑 NuttX 的 **UP 模式（单核）**，负责"管家"类活儿——系统控制、和 AP 协调。
- **CPU1 / CPU2 = AP（Application Plane，应用面）**：跑 NuttX 的 **SMP 模式（对称多核双核）**，负责真正跑应用业务。

为什么这么分？打个比方：CP 像是"车间主任"，不亲自拧螺丝，但负责排产、发号施令；AP 两个核是"两个熟练工"，真正动手干活。主任和工人之间用专门的"对讲机"（RPTUN / RPMsg，详见 `./25-跨核通信-RPTUN.md`）沟通。

### 【图解】

```
            上电
             │
             ▼
        ┌─────────┐
        │  BootROM │ 芯片固化，最先跑
        └────┬─────┘
             │
   ┌─────────┼───────────────────────────┐
   ▼         ▼                            ▼
 CPU0(CP)  CPU1(AP)                    CPU2(AP)
 NuttX UP  NuttX SMP 双核              NuttX SMP 双核
 单核        (与 CPU2 组成一个 SMP 对)   (与 CPU1 组成一个 SMP 对)
   │             │                          │
   └───── RPTUN / RPMsg 核间对讲机 ─────────┘
          （CP 与 AP 通过 armino SDK + NuttX wrapper 衔接）
```

### 【实操步骤】

1. 建立"三核"心智模型：CP = 1 个单核 NuttX；AP = 2 个核组成的 SMP 双核 NuttX。
2. 后续看 `./20-芯片适配层架构.md` 时，留意代码里 `CONFIG_BK7258_CP` 与 `CONFIG_BK7258_AP` 两类配置的区别。
3. 想提前了解核间通信，先 bookmark `./25-跨核通信-RPTUN.md`。

### 【背景知识】

> 💡 **什么是核？** "核（core）"就是芯片里真正能一条条执行指令的计算单元。一个核同一时刻只能干一件事（靠"任务切换"显得像同时干很多事）。多个核就能真的并行干活。本项目有 3 个核，所以能"一边联网、一边跑算法、一边控制外设"。

## 模块三：主频、存储与地址空间

### 【理论】

- **主频**：芯片内部时钟上限可达 **DPLL ~480MHz**（非当前目标），当前产品路径采用**已验证稳定的 320MHz 运行时 DVFS**（DVFS = 动态调频调压，就是"忙时拉高频率、闲时降频省电"）。
- **Flash（模组内置 SiP）**：约 **8MiB**，逻辑基址 `0x02000000`。注意末尾 **`0x7fa000 .. 0x800000` 是校准尾区，绝对不能动**（里面存着射频校准等出厂数据）。
- **PSRAM（模组内置 SiP）**：**16MiB**（型号 APS128XXO），用来当"大号内存"放运行数据。
- **调试接口**：**SWD**（当前板级验证路线 `P0=SWCLK`、`P1=SWDIO`；`P20/P21` 为编译可用的备选）。

### 【图解】

```
   地址空间（逻辑视图，单位 MiB）
   0x0200_0000 ┌──────────────────────────┐
               │  Flash 8MiB               │
               │  ├─ BL1 (XIP@0x02000000)  │
               │  ├─ BL2 MCUboot           │
               │  ├─ NuttX CP / AP 镜像     │
               │  └─ ...                   │
               │  ⚠ 0x7fa000..0x800000     │  ← 校准尾区，禁止写入
               └──────────────────────────┘
   模组内置SiP  ┌──────────────────────────┐
               │  PSRAM 16MiB (APS128XXO) │  ← 运行期大内存
               └──────────────────────────┘
   片内 SRAM  ┌──────────────────────────┐
               │  小容量高速 RAM           │  ← 启动早期/关键数据
               └──────────────────────────┘
```

### 【实操步骤】

1. 记住三个关键数字：**Flash 8MiB @0x02000000、PSRAM 16MiB（均为模组内置）、校准尾区 0x7fa000-0x800000 不动**。
2. 之后看分区布局 `./13-Flash分区布局.md` 时，会看到这些数字怎么被切成一个个"槽位"。
3. 调试连线：把 J-Link 的 SWCLK/SWDIO 接到模组 `P0/P1`（当前板级验证路线，详见 `./02-开发环境与工具链.md`）。

### 【背景知识】

> 💡 **为什么"校准尾区不能动"？** 芯片出厂时，厂家测得每颗芯片射频的微小差异，把补偿参数写进 Flash 最后那一小块。如果你烧固件时误覆盖了它，Wi-Fi/蓝牙可能就无法正常工作，且很难排查。所以分区设计专门给它留了"保护区"。

## 模块四：外设全家福

### 【理论】

BK7258 内置非常丰富的外设（外设 = 芯片上用来和外部世界打交道的硬件接口），清单：

Wi-Fi6 / BLE5.4 / GPIO / UART / I2C / SPI / I2S / SDIO / QSPI / PWM / CAN / DVP / LCD / USB / ETH / RTC / Timer / WDT / TRNG / SARADC / 温度 / 音频 / Mailbox。

在 open-vela / NuttX 移植里，这些外设大部分通过 **armino SDK 的 `bk_*` 函数** 来驱动（本项目驱动"零寄存器访问"，详见 `./03-基础概念铺垫.md` 与 `./22-驱动适配范式.md`）。

### 【图解】

```
   通信类：  UART  I2C  SPI  I2S  SDIO  QSPI  CAN  USB  ETH  Wi-Fi  BLE
   控制类：  GPIO  PWM  (Mailbox 核间)
   模拟类：  SARADC  温度传感  TRNG(随机数)
   时基类：  RTC(实时时钟)  Timer(定时器)  WDT(看门狗)
   图像类：  DVP(摄像头)  LCD(屏)
   音频类：  音频接口
```

### 【实操步骤】

1. 先混个脸熟，不用记全。重点关注你项目要用到的几个（如 I2C/PWM/GPIOE 见 `./23-外设驱动详解-一(I2C-PWM-GPIOE).md`，RTC/Timer/ADC 见 `./24-外设驱动详解-二(RTC-Timer-ADC).md`）。
2. 想看某个外设在 SDK 里有哪些 `bk_*` 接口，去 `./21-armino-SDK集成.md` 找入口。

### 【背景知识】

> 💡 **外设是什么？** CPU 自己只会算数，不会"发串口数据""读传感器电压"。这些"对外打交道"的硬件模块就叫外设。每个外设背后都有一组寄存器，但本项目里你**不用直接碰寄存器**，而是调用 SDK 封装好的函数——这正是后面要讲的 HAL / 驱动分层思想。

## 模块五：软件启动栈（从通电到 NuttX）

### 【理论】

芯片通电后，不是直接跑操作系统，而是**一级一级地把系统"叫醒"**。本项目的完整软件栈是：

```
BootROM(芯片固化)
   → 自研 Tier-1 BL1(板级, XIP@0x02000000)
      → MCUboot BL2(双副本 Primary/Secondary @0x024d0000 / 0x024f0000)
         → NuttX(CP=CPU0 单核 + AP=CPU1/2 双核 SMP)
```

- **BootROM**：芯片出厂固化在 ROM 里，上电第一句就它跑，负责最基础的搬运。
- **BL1（Tier-1）**：我们**自己写**的第一级 Bootloader，板级相关，直接就在 Flash 上运行（XIP，详见 `./03-基础概念铺垫.md`）。
- **BL2（MCUboot）**：用开源的 **MCUboot** 框架做第二级，负责**验签、选槽、跳转**——决定跑哪个固件副本、固件是否被篡改。
- **NuttX**：真正的操作系统，CP 单核 + AP 双核 SMP。

CP 与 AP 之间通过 **armino SDK 静态库 + NuttX wrapper** 衔接，核间用 **RPTUN / RPMsg** 通信。

### 【图解】

```mermaid
flowchart LR
    BR[BootROM\n芯片固化] --> BL1[BL1\n自研 Tier-1\nXIP@0x02000000]
    BL1 --> BL2[BL2\nMCUboot\nPrimary@0x024d0000\nSecondary@0x024f0000]
    BL2 --> CP[NuttX CPU0\nCP 单核 UP]
    BL2 --> AP[NuttX CPU1/2\nAP 双核 SMP]
    SDK[armino SDK\n静态库] -.wrapper.-> CP
    SDK -.wrapper.-> AP
    CP <==> AP
    style BR fill:#eee
    style BL1 fill:#cfe
    style BL2 fill:#cfc
    style CP fill:#fec
    style AP fill:#fec
```

### 【实操步骤】

1. 把上面这条链背下来或抄在草稿纸上：**ROM → BL1 → BL2 → NuttX**。
2. 想知道每一步具体干了啥，按顺序读 `./10-Bootloader总览与启动链.md` → `./11-BL1深度解析.md` → `./12-BL2-MCUboot深度解析.md`。
3. 想看"双副本 / 槽位"是怎么回事，先 bookmark `./13-Flash分区布局.md`。

### 【背景知识】

> 💡 **为什么不直接跑 NuttX？** 操作系统镜像往往很大，且需要"先初始化内存、再校验完整性、再决定从哪个副本启动"。这些活儿让一个小小的、确定性的 Bootloader 先干最稳妥。就像你早上先睁眼、再穿衣服、再出门，而不是闭着眼直接冲出门。

## 模块六：项目目标与仓库布局

### 【理论】

**项目目标**：把 **openvela / NuttX** 移植到 BK7258（涂鸦 T5-AI 模组），并参加 **2026 首届 openvela AI 硬件开发者大赛**。

**仓库设计的关键点**（很重要，新手常困惑）：

- 本仓库（`contest2026_135_yongwangzhiqian/`）**只承载 team overlay**——也就是"板级适配 + 自研驱动 + 自研 bootloader"这部分我们自己的活儿。
- 它通过 **repo manifest 的 `<linkfile>`** 机制，把自己的目录**软链接（符号链接）**进外层 openvela 编译树。
- 外层的 `nuttx/`、`apps/` 是**公共仓库，零改动**——我们不碰它们，只在自己这一层做适配。

一句话：**公共代码不动，自己的适配通过软链"挂"进去编译。**

### 【图解】

```
   openvela 外层编译树 (公共, 不修改)
   ├── nuttx/        ← 公共内核仓库 (零改动)
   ├── apps/         ← 公共应用仓库 (零改动)
   └── (通过 manifest <linkfile> 软链)
            │
            ▼  符号链接挂入
   contest2026_135_yongwangzhiqian/   ← 本仓 = team overlay
   ├── board/bk7258/   (板级适配 + BL1 Makefile)
   ├── tools/bk7258/   (构建/打包/调试脚本)
   ├── docs/bk7258-t5ai/ (文档)
   └── ... 自研驱动 / 自研 bootloader
```

### 【实操步骤】

1. 确认本仓位置：
   ```bash
   ls /home/lijian/project/open-vela/contest2026_135_yongwangzhiqian/
   ```
2. 理解"软链而非 copy"：本仓代码已经被 manifest 软链进编译树，你改本仓文件，编译时直接用，**不需要手动复制**。
3. 构建入口在**工作区根** `/home/lijian/project/open-vela`，用统一 `./build.sh <board-config-path>`（详见 `./02-开发环境与工具链.md`）。

### 【背景知识】

> 💡 **什么是 overlay（覆盖层）？** 想象公共代码是一本"标准教材"，你不想在教材上乱涂乱画，就另外拿一本活页夹，把自己补充的章节插进去一起用。overlay 就是这个"活页夹"——只放你自己的差异部分，公共教材保持原样，方便以后同步官方更新。
