## 模块一：Bootloader 是什么（上电为啥不直接跑应用）

### 【理论】

**Bootloader（引导程序）** 就是芯片上电后跑的第一小段程序，它的任务是"把真正能干活的软件（操作系统/应用）唤醒并交棒"。

为什么上电不直接跑应用？因为芯片刚通电时，**内存还没初始化、时钟还没稳住、外设还不能用**，应用根本没法直接跑。必须先有一小段"极简且可靠"的代码，把最基础的环境搭好，再把应用从 Flash 搬起来、跳过去执行。

打比方：你早上醒来，不会闭着眼直接冲出门上班——而是先睁眼、穿衣、洗漱（Bootloader），状态准备好了才出门干活（应用）。

### 【图解】

```
   上电复位
      │
      ▼
   ┌──────────────┐
   │  Bootloader   │  初始化时钟/内存/最小外设
   │  (一小段)     │  把应用从 Flash 搬好
   └──────┬───────┘
          │ 跳过去 (跳转指令)
          ▼
   ┌──────────────┐
   │   应用/OS     │  真正干活
   └──────────────┘
```

### 【实操步骤】

1. 记住一句话：**上电先跑 Bootloader，再由它启动操作系统。**
2. 想看本项目的 Bootloader 长什么样，按顺序读 `./10-Bootloader总览与启动链.md` → `./11-BL1深度解析.md`。
3. 接上 UART 控制台（见 `./02-开发环境与工具链.md`），上电后观察：最早打印出来的往往是 BL1/BL2 的日志，最后才是 NuttX。

### 【背景知识】

> 💡 **没学过嵌入式也要懂**：你家的电脑开机也是这个套路——先跑主板上固化的 BIOS/UEFI（相当于 Bootloader），它检测内存、硬盘，再把 Windows/Linux 启动起来。芯片同理，只是更小、更精简。

## 模块二：BL1 / BL2 分级启动的意义（为什么需要两级）

### 【理论】

本项目启动分两级：**BL1（Tier-1，自研）** 和 **BL2（MCUboot）**。为什么要分两级，而不是一段搞定？

- **BL1** 追求"最小、最可信"：它直接在 Flash 上运行（XIP），只做最早期的硬件初始化，并把 BL2 链起来。它代码少、逻辑简单，容易被审计和信任。
- **BL2（MCUboot）** 功能多：要验签、要选副本、要跳转，逻辑复杂。复杂的代码不能一上电就跑（环境还没好，且攻击面大），所以需要一个简单的 BL1 先把舞台搭好，再交给 BL2。

分级的本质是**"责任分离 + 安全启动的可信根"**：最底层那段极小极可靠，作为信任起点，再去验证上一层。

### 【图解】

```
   上电
    │
    ▼
   BL1 (极小/可信)  ── 初始化最基础硬件, 链起 BL2
    │
    ▼
   BL2 (MCUboot)   ── 验签 + 选槽 + 跳转
    │
    ▼
   NuttX (操作系统)

   类比：保安开门(BL1) → 前台核验身份发门禁卡(BL2) → 员工进办公区(NuttX)
```

### 【实操步骤】

1. 记住"两级"的分工：BL1 = 搭台子；BL2 = 验票选座。
2. BL1 怎么编译、怎么 XIP，见 `./11-BL1深度解析.md`。
3. BL2 的验签与双副本，见 `./12-BL2-MCUboot深度解析.md`。

### 【背景知识】

> 💡 **什么是"可信根（Root of Trust）"？** 就像一条信任链，必须有个"绝对可信的第一环"，后面每环都验证下一环。BL1 就是这条链的第一环——它简单到可以被完全审查，于是我们敢信任由它启动的一切。

## 模块三：MCUboot 是什么

### 【理论】

**MCUboot** 是一个**开源的 Bootloader 框架**（现成的"轮子"），专门给 MCU（微控制器）做固件引导。它在本项目里充当 **BL2**，核心三件事：

1. **验签**：检查固件是不是官方签发的、有没有被篡改（详见模块十一）。
2. **选槽（slot）**：支持双副本（A/B 备份），启动时发现主副本坏了，自动切到备副本。
3. **跳转**：确认无误后，跳到选中的固件去执行。

本项目里 MCUboot 的双副本地址：Primary `@0x024d0000`、Secondary `@0x024f0000`。

### 【图解】

```
   MCUboot (BL2)
   ┌─────────────────────────────┐
   │  验签固件? ──否──► 拒绝启动   │
   │     │ 是                      │
   │     ▼                        │
   │  选槽: Primary 完好?          │
   │    ├─ 是 ─► 跳 Primary       │
   │    └─ 否 ─► 跳 Secondary(备份)│
   └─────────────────────────────┘
```

### 【实操步骤】

1. 记住 MCUboot = "开源的 BL2 管家：验票 + 选座 + 带位"。
2. 想知道双副本怎么排、怎么切换，读 `./12-BL2-MCUboot深度解析.md` 与 `./13-Flash分区布局.md`。
3. 想动手打包/烧录双副本，见 `./30-构建-烧录-调试实战.md`。

### 【背景知识】

> 💡 **什么是"框架（framework）"？** 就是别人写好的、半成品的"脚手架"。你不用从零造轮子，只要按它的规矩填自己的部分（比如"固件放哪、怎么验签"），就能直接用。MCUboot 就是 bootloader 领域的成熟脚手架。

## 模块四：XIP（Execute In Place）是什么

### 【理论】

**XIP = 原地执行**：代码**不拷贝到 RAM，而是直接在 Flash 上取指令执行**。

- 好处：省 RAM。Flash 有 8MiB，而片内 SRAM 只有 640KB，如果所有代码都搬进 RAM 根本放不下。
- 代价：Flash 比 RAM 慢，所以 XIP 的代码执行速度不如在 RAM 里跑。
- 本项目 **BL1 就是 XIP**，运行在 `0x02000000`（Flash 逻辑基址）。

### 【图解】

```
   普通方式(非 XIP)：
   Flash ──拷贝代码──► RAM ──CPU 从 RAM 取指执行
   （占 RAM，但快）

   XIP 方式：
   Flash ──CPU 直接从 Flash 取指执行──► （不占 RAM，但慢）
   本项目 BL1 @0x02000000 即如此
```

### 【实操步骤】

1. 记住：BL1 在 Flash 上直接跑，地址 `0x02000000`。
2. 看 BL1 的链接地址为什么是这个值，见 `./11-BL1深度解析.md`。
3. 对照模块五，理解"为什么 BL1 能 XIP、而大块 NuttX 往往要先搬"——因为 SRAM 装不下全部。

### 【背景知识】

> 💡 **取指（fetch）是什么？** CPU 执行程序，就是不断从内存"取一条指令→执行→再取下一条"。取指从哪取，代码就在哪跑。XIP 就是"取指的位置 = Flash 本身"。

## 模块五：SRAM / PSRAM / Flash 的区别

### 【理论】

芯片里有好几类"存储器"，速度、是否掉电丢失、用途都不同。本项目三种：

| 类型 | 易失性 | 速度 | 容量/位置 | 用途 |
|------|--------|------|-----------|------|
| **Flash** | 非易失（掉电不丢） | 慢 | 模组内置 ~8MiB @0x02000000 | 存代码/固件（长期） |
| **SRAM** | 易失（掉电丢） | 最快 | 片内共享 640KB | 启动早期/关键变量 |
| **PSRAM** | 易失（掉电丢） | 较快 | 模组内置 16MiB (APS128XXO) | 运行期大块数据 |

- **易失性**：断电后数据是否还在。Flash 像"笔记本"（写完一直在）；SRAM/PSRAM 像"白板"（断电就擦掉）。
- 所以：程序**代码**放 Flash（要长期留着），**运行中的数据**放 SRAM/PSRAM（掉电无所谓）。

### 【图解】

```
   快 ─┐
       │  SRAM   片内共享 640KB  关键/早期
       │  PSRAM  模组内置 16MiB  运行期大数据
   慢 ─┘  Flash   模组内置 8MiB  固件(非易失)
        （速度越快越贵越小，越慢越便宜越大）
```

### 【实操步骤】

1. 背下三数字：**Flash 8MiB（模组内置，非易失）、PSRAM 16MiB（模组内置）、SRAM 片内 640KB（最快）**。
2. 记住铁律：**代码固件进 Flash，运行数据进 SRAM/PSRAM**。
3. 注意 Flash 尾区 `0x7fa000..0x800000` 是校准区，禁止写（见 `./01-芯片与项目背景.md`）。

### 【背景知识】

> 💡 **为什么不全用最快的 SRAM？** 越快的内存越贵、越占芯片面积，所以容量做不大。工程上用"分层"策略：少量最快的放关键数据，大量便宜的 Flash 放固件——和电脑里"内存 + 硬盘"是一个思路。

## 模块六：链接脚本（linker script / .ld）的作用

### 【理论】

**链接脚本（`.ld` 文件）** 告诉**链接器**：把程序的每一段（代码 `.text`、已初始化数据 `.data`、未初始化数据 `.bss` 等）放到**哪个具体内存地址**。

为什么关键？因为芯片是从**固定的地址**开始取指执行的。如果你的代码被链接到了错误的地址（比如本该在 Flash `0x02000000`，却链到了 RAM 地址），芯片一上电就找不到正确指令，直接跑飞。

一句话：**`.ld` 决定"代码和数据住在内存的哪个门牌号"。**

### 【图解】

```
   多个 .o 目标文件
        │
        ▼
   链接器 (ld)  +  board/bk7258/ 下的 .ld 脚本
        │  按脚本安排地址
        ▼
   带绝对地址的固件 (bin/elf)
   .text → Flash 0x02000000
   .data → 某 RAM 区
   .bss  → 某 RAM 区
```

### 【实操步骤】

1. 在板级目录里找链接脚本感受一下（文件名以 `.ld` 结尾）：
   ```bash
   find /home/lijian/project/open-vela/contest2026_135_yongwangzhiqian/board/bk7258 -name '*.ld'
   ```
2. 打开任意一个 `.ld`，看里面的 `MEMORY` / `ORIGIN` 关键字，它就是"门牌号分配表"。
3. 回想模块四：BL1 能 XIP，正是因为它的 `.ld` 把代码链到了 Flash 基址 `0x02000000`。

### 【背景知识】

> 💡 **编译 vs 链接 有啥区别？** 编译是把单个 `.c` 变成 `.o`（目标文件，地址还是"相对/假的"）；链接是把多个 `.o` 拼成最终文件，并**分配真实内存地址**——这一步才用得到 `.ld` 脚本。

## 模块七：什么是 RTOS（以及 NuttX）

### 【理论】

**RTOS = 实时操作系统（Real-Time Operating System）**。和电脑上的 Windows/Linux 相比，它**小、确定性强、能在单片机这种资源紧张的设备上跑**。

**NuttX** 是其中一个开源 RTOS，特点是"类 POSIX"（很多接口和 Linux 像），支持多任务、文件系统、网络等。

**为什么嵌入式要用操作系统？** 没有 OS，你得自己写"任务调度、内存管理、外设管理"，复杂度爆炸；有了 NuttX，这些脏活它包了，你只要写"业务任务"。

打比方：没 OS 像一人公司，老板(CPU)啥都自己干；有 OS 像有了经理(内核)，把活分给不同员工(任务)并调度。

### 【图解】

```
   应用任务A ┐
   应用任务B ├─► NuttX 内核(调度/内存/设备框架) ─► 硬件(CPU/外设)
   应用任务C ┘
```

### 【实操步骤】

1. 记住：本项目跑的就是 **NuttX**（CP 单核 + AP 双核，见 `./01-芯片与项目背景.md`）。
2. 烧录启动后，串口会进 **NSH**（NuttX Shell，类似命令行），可以敲命令看系统状态。
3. 想深入内核与板级适配的关系，读 `./20-芯片适配层架构.md`。

### 【背景知识】

> 💡 **什么是"任务/进程/调度"？** 任务就是"一段要被执行的逻辑"。单核同一时刻只能跑一个任务，OS 用"调度"快速切换，让人觉得多个任务"同时"跑（其实是在极快轮流执行）。实时（Real-Time）强调"该响应的时候能准时响应"。

## 模块八：AMP vs SMP，以及本项目的 CP/AP 模型

### 【理论】

多核芯片有两种组织方式：

- **AMP（非对称多核）**：不同核跑**不同的系统/不同的活**，各管一摊，彼此像"两个不同部门"。
- **SMP（对称多核）**：多个核**同构**，跑**同一个系统**，任务可以随便分到任一核上，像"一组相同的工人，活均匀分"。

本项目是 **混合模型**：
- **CPU0 = CP（控制面）**：NuttX **UP 单核**（非对称地专门做控制）。
- **CPU1/CPU2 = AP（应用面）**：NuttX **SMP 双核**（两个相同工人跑同一系统）。

即"1 个 CP 单核 + 1 对 AP 双核 SMP"。三者通过 RPTUN/RPMsg 通信（见 `./25-跨核通信-RPTUN.md`）。

### 【图解】

```
   ┌─────────────┐      RPTUN/RPMsg       ┌──────────────────┐
   │ CPU0: CP     │ ◄══════ 对讲机 ══════► │ CPU1+CPU2: AP     │
   │ NuttX UP 单核 │                        │ NuttX SMP 双核    │
   │ (控制/协调)   │                        │ (业务/应用)       │
   └─────────────┘                        └──────────────────┘
     AMP 风格                                 SMP 风格
```

### 【实操步骤】

1. 记住模型：**1 个 CP 单核 + 1 对 AP 双核 SMP**。
2. 看代码里的 `CONFIG_BK7258_CP` 与 `CONFIG_BK7258_AP` 两类配置含义（见 `./20-芯片适配层架构.md`）。
3. 想搞懂核间怎么传消息，读 `./25-跨核通信-RPTUN.md`。

### 【背景知识】

> 💡 **单核 vs 多核 再复习**：一个核同一时刻干一件事；多核能真并行。SMP 的好处是"加核就能加算力，程序不用大改"；AMP 的好处是"关键控制和业务隔离，互不拖累"。本项目把两者结合用。

## 模块九：什么是设备驱动，以及 NuttX 的 upper-half / lower-half 分层

### 【理论】

**设备驱动（driver）** 就是"让操作系统能操作某个硬件"的软件。没有驱动，OS 不知道怎么跟 GPIO、UART 这些硬件说话。

NuttX 把驱动分成两层，解耦得很清楚：

- **upper-half（上半层）**：**与硬件无关**的通用部分。它向应用提供统一的字符设备接口（如 `open/read/write`），应用只跟它打交道，不关心底下是哪家芯片。
- **lower-half（下半层）**：**与硬件相关**的具体部分。真正去操作芯片寄存器/调用 SDK，把"写数据"变成"硬件动作"。

应用 → upper-half（统一接口）→ lower-half（具体硬件）→ 物理外设。

### 【图解】

```
   应用代码
      │ open/read/write (标准接口)
      ▼
   upper-half  (通用, 与芯片无关)
      │ 调用
      ▼
   lower-half  (具体芯片操作)
      │
      ▼
   硬件外设 (GPIO/UART/I2C...)
```

### 【实操步骤】

1. 记住分层口诀：**上半层管"对应用长啥样"，下半层管"对硬件怎么动"。**
2. 看本项目驱动怎么写，读 `./22-驱动适配范式.md`。
3. 具体外设（I2C/PWM/GPIOE）示例，见 `./23-外设驱动详解-一(I2C-PWM-GPIOE).md`。

### 【背景知识】

> 💡 **为什么要分层？** 为了"解耦"。如果应用直接写死某款芯片的寄存器，换芯片就得改全部应用。分层后，应用只认统一接口，换芯片只需换 lower-half——应用代码一行不动。这就是软件工程里"面向接口编程"的思想。

## 模块十：HAL（硬件抽象层），以及本项目"零寄存器访问"

### 【理论】

**HAL = 硬件抽象层（Hardware Abstraction Layer）**：把"直接读写芯片寄存器"这种底层、易错、难移植的操作，**封装成一组友好函数**。

本项目的特色正是**驱动"零寄存器访问"**：我们写驱动时**不直接碰 BK7258 的寄存器**，而是只调用 **armino SDK 提供的 `bk_*` 函数**（如 `bk_gpio_xxx`、`bk_i2c_xxx`）。这些 `bk_*` 函数内部才去操作寄存器。

好处：
- **可移植**：驱动代码不绑定寄存器细节，SDK 升级/换芯片时驱动改动小。
- **不易错**：寄存器位操作很容易写错，交给经过验证的 SDK 更稳。

### 【图解】

```
   本项目驱动代码
      │  只调用
      ▼
   armino SDK 的 bk_* 函数   ← 硬件抽象层(HAL)
      │  内部才操作
      ▼
   BK7258 寄存器 (我们不直接碰)
```

### 【实操步骤】

1. 记住一句话：**本项目驱动 = "只调 bk_*，不写寄存器"。**
2. 想看 SDK 里有哪些 `bk_*` 接口，读 `./21-armino-SDK集成.md`。
3. 看一个真实驱动的写法，读 `./22-驱动适配范式.md` 与 `./23-外设驱动详解-一(I2C-PWM-GPIOE).md`。

### 【背景知识】

> 💡 **寄存器是什么？** 芯片把"控制自己的开关"做成一组内存地址，写不同的值就产生不同硬件行为（比如"把某位设 1 = 点亮 LED"）。直接操作它们叫"寄存器级编程"，功能最强但最繁琐、最易错。HAL 就是把这些操作包成"点亮LED()"这样的函数。

## 模块十一：镜像签名 / 验签（ECDSA-P256）的基本思想

### 【理论】

**签名/验签** 是为了**防止烧入被篡改的固件**。基本思想：

- 厂商用**私钥**对固件算出一个"数字签名"（类似盖章）。
- 芯片用对应的**公钥**验证：固件 + 签名 对得上 → 确实官方出品、没被改过 → 允许启动；对不上 → 拒绝启动。

本项目用的是 **ECDSA-P256**（一种椭圆曲线数字签名算法，P256 指 256 位密钥长度）。它是安全启动（见 `./14-安全启动与签名.md`）的技术底座。

### 【图解】

```
   出厂/发布时（签名）：
   固件 ──+──► [私钥] ──► 签名  ── 随固件一起烧入

   启动时（验签）：
   固件 + 签名 ──► [公钥验证] ── 通过? ──► 启动
                                  └─ 不通过 ──► 拒绝
```

### 【实操步骤】

1. 记住类比：**签名 = 公章，验签 = 验章；假章/改过的文件验不过就拒收。**
2. 想看本项目签名/验签怎么落地，读 `./14-安全启动与签名.md`。
3. 回忆模块二：BL2（MCUboot）正是负责"验签"那一环的。

### 【背景知识】

> 💡 **公钥 / 私钥 是什么？** 一对数学上关联的钥匙：私钥自己藏好（用来盖章），公钥可以公开（用来验章）。只知道公钥**无法反推私钥**，所以别人没法伪造你的签名——这是现代信息安全的基础。
