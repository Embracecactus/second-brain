# 26. 驱动注册与常见坑

> 目标：理解 NuttX 里驱动是怎么"注册"出来的，以及 BK7258 移植中反复踩过的那些坑——每个坑都配有"现象→原因→修法"。

---

## 26.1 理论：驱动是怎么出现在系统里的？

在 [22-驱动适配范式](./22-驱动适配范式.md) 里我们学会了"写一个驱动"：定义 ops 结构体 → 定义私有数据结构 → 调用注册函数。但注册函数是谁调用的？在系统启动的哪个时刻调用？这就是本模块要回答的问题。

NuttX 里驱动出现在系统中有**两条典型路径**：

| 路径 | 触发时机 | 典型调用点 | 适合场景 |
|---|---|---|---|
| **板级初始化** | 内核启动早期，`board_initialize()` 阶段 | `board/bk7258/src/bk7258_boardinit.c` | 固定板载外设（I2C、PWM、WDT） |
| **应用/模块初始化** | 应用启动后，由 NSH 命令或用户程序触发 | 自定义 `init` 程序 / NSH 启动脚本 | 可选外设、需按配置启用的外设 |

理解"什么时候注册"很重要，因为**注册太早可能硬件还没就绪，注册太晚应用会打开不到设备节点**。

---

## 26.2 图解：从注册函数到 `/dev/xxx`

```mermaid
flowchart LR
    A[board_initialize] -->|调用| B[i2c_register]
    B -->|创建设备节点| C[/dev/i2c0]
    C --> D[用户程序 open 成功]
    A -.->|需要 CONFIG 开关| E[CONFIG_BK7258_I2C]
    E -.->|编译时决定代码是否编译进去| A
```

> 💡 **背景知识：CONFIG_ 宏是编译期开关**
>
> NuttX 用 Kconfig 生成 `CONFIG_xxx` 宏。代码里的 `#ifdef CONFIG_BK7258_I2C` 在**编译时**决定这段代码存不存在。如果配置里没开这个开关，代码根本不会被编译进固件，运行时自然没有这个设备。
>
> 所以排查"为什么没有 /dev/i2c0"的第一步，永远是**先确认 CONFIG 开了没有**，而不是去翻驱动代码。

## 26.3 常见坑总览

下面是 BK7258 移植与驱动审查中反复出现的坑。每个都来自真实修复经验，按"现象→原因→修法"组织。

### 坑 1：符号缺失 / 功能没有 —— 先查 CONFIG 父开关

**现象**：驱动代码明明写好了，编译时却报"未定义引用"，或者编译过了但功能没有。

**原因**：NuttX 的 Kconfig 有层级关系（父选项没开，子选项不生效）。BK7258 的驱动挂在一级开关（如 `CONFIG_I2C`、`CONFIG_PWM`）和二级开关（如 `CONFIG_BK7258_I2C`）下。有时只开了二级开关、父开关被裁剪，或者反过来——**依赖树里某个开关没开，相关文件根本没进编译**。打包阶段最容易暴露：静态库里符号缺失，先怀疑的不是"SDK 没实现"，而是"配置开关被裁剪"。

**修法**：
```bash
# 1. 看最终配置里该开关是否生效
cd /home/lijian/project/open-vela
grep "CONFIG_BK7258_I2C" .config                 # 或生成的 sdkconfig.h
# 2. 看它的父开关
grep -E "CONFIG_(I2C|BK7258_I2C)" .config
```
一层层往上查，把依赖链上的父开关全部确认一遍。

### 坑 2：线程生命周期 —— join / 取消集合

**现象**：驱动内部创建的工作线程，在设备 `close()` 或驱动卸载时没有被正确回收；或者线程退出后代码还在等它，导致资源泄漏、野指针、甚至系统卡死。

**原因**：嵌入式里驱动线程常用 `pthread_create` 创建。如果主流程不等线程结束就释放了它依赖的内存/句柄，线程还在跑就访问了已释放的资源。

**修法**：关闭/卸载路径必须做"集合"：
- `pthread_join()` 等待线程真正退出，再释放资源。
- 或者用**取消集合**（cancel 点 + join）：发取消请求 → 等退出码 → 再释放。
- 线程内部要有明确的退出条件（标志位），不能只靠强杀。

### 坑 3：ISR 里读取多字节状态必须"快照"

**现象**：中断服务函数（ISR）里读外设状态寄存器，有时读到的是"撕裂"的值——高字节是新的、低字节是旧的，或两次读中间状态被硬件更新。

**原因**：中断可能在任何时刻被打断/被更紧急中断抢占。读一个 32 位状态寄存器不是原子操作，硬件可能在两次读之间更新了它。

**修法**：在 ISR 入口一次性把需要的寄存器**完整快照**进局部变量，后续所有判断都基于这个快照，不要在 ISR 里反复重读外设寄存器。
```c
void bk7258_xxx_isr(int irq, void *context)
{
  /* 先快照：只读一次 */
  uint32_t stat = getreg32(XXX_STATUS_REG);
  uint32_t mis  = getreg32(XXX_MIS_REG);

  /* 之后只用快照判断，不再重读寄存器 */
  if (stat & BIT(0)) { ... }
}
```

### 坑 4：并发启动竞态 —— 需要"running 门闩"

**现象**：驱动被重复打开/启动时行为异常：第二次 `start()` 要么重复初始化硬件，要么与正在运行的第一次互相干扰。

**原因**：没有状态门闩（latch）。驱动内部应有一个"是否已运行"的标志，第一次启动时置位，第二次进来直接返回已有实例或报错。

**修法**：用原子标志做门闩。
```c
static bool g_running;   /* 注意用 atomic 或关中断保护 */

static int bk7258_xxx_start(...)
{
  if (g_running)
    {
      return -EBUSY;      /* 已在运行，拒绝重复启动 */
    }
  g_running = true;
  ...
}
```

### 坑 5：SDK 函数语义想当然 —— 幂等性必须先核实

**现象**：调 `bk_xxx_init()` 时没问题，第二次调用（比如驱动重载）时行为诡异。

**原因**：SDK 的 HAL 函数语义**不一定幂等**。有的 `init` 二次调用会重复注册中断、重复申请内存；有的 `deinit` 会清掉别的模块共享的寄存器。

**修法**：把"核实 SDK 语义"当成写驱动的前置步骤：
- 读 SDK 源码确认：init 可不可重入？能不能重复调用？
- 确认函数是阻塞还是非阻塞、消费队列还是旁路。
- 在 wrapper 层做幂等保护（见坑 4 的门闩）。

### 坑 6：配置没断言 —— 出问题才发现的开关依赖

**现象**：驱动依赖某个 CONFIG（如中断、DMA）没开，编译能过但运行就挂，且报错信息完全没有提示。

**原因**：代码里用了"可选"配置，但没在编译期做断言。理想情况是：**配置不满足就编译报错**，而不是运行时炸。

**修法**：在代码顶部加编译期断言。
```c
#if !defined(CONFIG_BK7258_XXX) || !defined(CONFIG_XXX_DMA)
#  error "CONFIG_BK7258_XXX 与 CONFIG_XXX_DMA 必须同时开启"
#endif
```

### 坑 7：设备节点权限 / 打开顺序

**现象**：应用 `open("/dev/i2c0")` 失败（ENOENT），但配置明明开了。

**原因**：除了 CONFIG 没开（坑 1），还有几种常见情况：
- 注册函数所在的 `board_initialize()` 分支被 `#ifdef` 掉了；
- 注册发生在应用启动**之后**（NSH 先跑、注册后跑）；
- 设备节点路径写错（如 `/dev/i2c0` vs `/dev/i2c/0`）。

**修法**：用 `ls /dev` 看节点是否存在；`ls -l /dev` 看权限；确认注册时机。

### 坑 8：硬件时钟 / 上拉没使能

**现象**：驱动逻辑全对，但外设就是不出波形、不收数据。

**原因**：很多 SoC 的外设需要先开外设时钟门控（clock gating）和 GPIO 复用（pinmux）/ 上拉配置。SDK 的 `bk_xxx_init()` 通常会做，但**前提是 GPIO 配置对**（引脚号、复用功能、上拉）。有时 SDK 不管 GPIO，需要驱动自己配。

**修法**：对照数据手册确认引脚复用表；查看 SDK 里 `gpio_initialize`/`pinmux` 相关调用；用逻辑分析仪/示波器验证波形。

```mermaid
flowchart TD
    A[/dev/xxx 不存在或异常] --> B{先查 CONFIG 开关?}
    B -- 没开 --> C[按依赖链逐层开父开关 坑1]

    J -- 是 --> K[寄存器快照 坑3]

```

## 26.5 实操：验证一个 CONFIG 是否真的进了编译

```bash
cd /home/lijian/project/open-vela
# 1. 看最终生效的配置
grep -E "CONFIG_(I2C|BK7258_I2C)" .config
# 2. 看编译产物里有没有对应符号
grep -rn "bk7258_i2c_register\|i2c_register" nuttx/nuttx.map   # 或 objdump
```

如果 `.config` 里没有，就是配置问题（坑 1/6）；如果有但 map 文件里没有符号，可能是父开关裁剪（坑 1）。

## 26.7 本节小结

- 驱动注册有两条路径：板级初始化（`board_initialize`）与应用/模块初始化。
- **设备不存在先查 CONFIG，符号缺失先查父开关**——这是第一条铁律。
- 六大真实修复模式：线程 join/取消集合、ISR 快照、running 门闩、SDK 幂等核实、配置断言、硬件配置确认。
- 排查路径：CONFIG → 节点 → 注册时机 → 并发 → ISR → SDK 语义 → 硬件。
