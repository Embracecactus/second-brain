# 开发环境与工具链

> 这一篇教你"在哪里敲命令、用什么工具、烧录用什么、调试怎么连"。
> 目标：读完你能在自己机器上**定位构建入口、认识关键脚本、知道烧录和调试工具分别在哪**。

---

## 模块一：构建在哪里进行（工作区根）

### 【理论】

所有构建动作都在 **工作区根** `$WORKSPACE` 进行。

NuttX 在本项目里有一个**统一入口脚本**：`./build.sh <board-config-path>`。你不用去记一大串 make 命令，只要把"板级配置路径"作为参数传给 `build.sh` 就行。`build.sh` 本身位于工作区根：
`$WORKSPACE/build.sh`

> 关于 `<board-config-path>` 具体填什么，本文不臆造具体值，请见 **`./30-构建-烧录-调试实战.md`** 与权威 SOP `docs/bk7258-t5ai/nuttx-port/bk7258-build-flash-debug-sop.md`。

### 【图解】

```
   $WORKSPACE/      ← 工作区根（构建在这里跑）
   ├── build.sh                         ← 统一构建入口
   ├── nuttx/        (公共, 软链挂入)
   ├── apps/         (公共, 软链挂入)
   └── ... 外层 openvela 编译树

   你只需：
   $ cd $WORKSPACE
   $ ./build.sh <board-config-path>
```

### 【实操步骤】

1. 进入工作区根：
   ```bash
   cd $WORKSPACE
   ```
2. 确认 `build.sh` 存在：
   ```bash
   ls -l build.sh
   ```
3. 确认本仓已通过 manifest `<linkfile>` 软链进编译树（无需手动 copy）：
   ```bash
   ls -l $CONTEST
   ```

### 【背景知识】

> 💡 **什么是"工作区根"？** 就是整个工程最顶层文件夹。所有相对路径、脚本都默认从这里出发。把命令都在这个目录里跑，能避免"找不到文件"的尴尬。

## 模块二：编译工具链（编译器 + Python）

### 【理论】

要生成芯片能跑的机器码，需要两样东西：

- **arm-none-eabi-gcc**：ARM 官方的交叉编译器（cross compiler）。"交叉"指你在 x86 电脑上编译，生成的是给 ARM 芯片跑的程序。本项目验证过 **10.3 版本**。
- **Python3**：大量构建/打包/校验脚本都是 Python 写的（下面模块三会列）。

"交叉编译"打比方：你在厨房（电脑）写好菜谱并备好料（编译），但真正下锅炒是在另一个城市的餐馆（ARM 芯片）。编译器就是那个"按芯片口味备料"的工具。

### 【图解】

```
   你的电脑 (x86_64, Linux/WSL)
   ┌──────────────────────────────┐
   │  arm-none-eabi-gcc 10.3       │ 把 C 代码 → ARM 机器码
   │  Python3                      │ 跑构建/打包/校验脚本
   └──────────────┬───────────────┘
                  │ 生成的 .bin/.elf
                  ▼
   BK7258 芯片 (ARM Cortex-M33)  ← 真正执行
```

### 【实操步骤】

1. 检查交叉编译器版本（应为 10.3 或兼容）：
   ```bash
   arm-none-eabi-gcc --version
   ```
2. 检查 Python：
   ```bash
   python3 --version
   ```
3. 若 `arm-none-eabi-gcc` 不存在，请按权威 SOP `docs/bk7258-t5ai/nuttx-port/bk7258-build-flash-debug-sop.md` 安装工具链（本文不臆造安装命令）。

### 【背景知识】

> 💡 **为什么叫"交叉"编译器？** 普通编译器在你自己电脑上编、自己电脑上跑。但嵌入式芯片的 CPU 架构和你的电脑不同，所以需要一个"在 A 机器上编、给 B 机器跑"的编译器，这就是交叉编译器。名字里的 `none-eabi` 表示"不带操作系统标准库接口"（裸机/RTOS 用）。

## 模块三：关键工具脚本一览

### 【理论】

本仓 `tools/bk7258/` 下有一批脚本，初学者先认识下面 5 个最常用的（其余是进阶/校验用途，用到再查）：

| 脚本 | 作用 |
|------|------|
| `bk7258_framework.py` | 产品构建计划（build plan）的解析与校验 |
| `materialize_product_profiles.py` | 渲染临时的 "role view"（产品角色视图） |
| `build_package.sh` | 把 BL1 + BL2 + CP + AP 打包成 `firmware.bkpack` |
| `bk7258_auto_debug.sh` | 一键自动构建 + 稀疏烧录 + 结果判读 |
| `board/bk7258/bootloader/Makefile` | 编译 BL1 的 Makefile |

这些脚本的真实路径前缀都是：
`$CONTEST/`

### 【图解】

```
   tools/bk7258/
   ├── bk7258_framework.py         解析/校验 产品构建计划
   ├── materialize_product_profiles.py   渲染临时 role view
   ├── build_package.sh            打包 → firmware.bkpack
   └── bk7258_auto_debug.sh        自动构建+稀疏烧录+判读

   board/bk7258/bootloader/
   └── Makefile                    编译 BL1
```

### 【实操步骤】

1. 列出本仓工具脚本目录，混个脸熟：
   ```bash
   ls $CONTEST/tools/bk7258/
   ```
2. 看框架脚本的帮助（了解它能解析什么）：
   ```bash
   python3 $CONTEST/tools/bk7258/bk7258_framework.py --help
   ```
3. 确认 BL1 的 Makefile 存在：
   ```bash
   ls $CONTEST/board/bk7258/bootloader/Makefile
   ```

### 【背景知识】

> 💡 **什么是"打包成 bkpack"？** 最终能烧进芯片的不是单个文件，而是 BL1、BL2、CP、AP 好几段拼起来的"整包"。`build_package.sh` 就像一个"装箱工"，把各部分按正确顺序拼成 `firmware.bkpack` 这个出厂固件包。

## 模块四：软链机制（为什么不用手动 copy）

### 【理论】

回顾 `./01-芯片与项目背景.md` 讲的仓库布局：本仓是 team overlay，通过 **repo manifest 的 `<linkfile>`** 软链进外层 openvela 编译树。

对初学者最重要的实操含义是：**你只改本仓 `contest2026_135_yongwangzhiqian/` 下的文件，编译时外层 `nuttx/` 会直接看到它们，不需要你手动复制粘贴。** 这避免了"改了 A 但编译用的是 B"的经典陷阱。

### 【图解】

```
   你编辑： contest2026_135_yongwangzhiqian/board/bk7258/...
                     │
                     │  manifest <linkfile> 建立的软链接
                     ▼
   编译时读取： openvela 编译树里的对应位置（其实是同一份文件）
```

### 【实操步骤】

1. 验证软链确实存在（以某个被挂入的路径为例，具体链接名见 SOP）：
   ```bash
   ls -l $CONTEST/
   ```
2. 记住铁律：**改本仓 = 改编译树，别去手动 copy。**

### 【背景知识】

> 💡 **什么是软链接（symbolic link）？** 类似 Windows 的"快捷方式"。编译系统以为自己在读 A 文件，其实 A 是个指针，指向你本仓的 B 文件。所以改 B，A 立刻生效。

## 模块五：烧录工具（把固件写进芯片）

### 【理论】

"烧录"（flash）就是把编译好的固件写进芯片的 Flash 里。本项目用 **Beken 官方的烧录工具 `bk_loader.exe`**（也叫 BKFIL）：

- 它运行在 **Windows 侧**。
- 在 **WSL** 环境里可以**调用**它（即你在 WSL 命令行触发，实际由 Windows 程序执行）。
- 下载（烧录）使用的端口是 **COM3**（下载口）。

> 具体怎么唤起 `bk_loader.exe`、参数怎么写，本文不臆造，请见权威 SOP `docs/bk7258-t5ai/nuttx-port/bk7258-build-flash-debug-sop.md` 与 `tools/bk7258/bk7258_auto_debug.sh`（自动烧录逻辑）。

### 【图解】

```
   WSL (Linux 命令行)
        │  调用
        ▼
   Windows: bk_loader.exe (Beken BKFIL)
        │  通过串口
        ▼
   模组下载口 = COM3  ──►  BK7258 Flash
```

### 【实操步骤】

1. 确认 Windows 侧 `bk_loader.exe` 可用（在 Windows 里能找到该程序）。
2. 确认模组下载口在 Windows 设备管理器里显示为 **COM3**。
3. 最简方式：用自动脚本 `bk7258_auto_debug.sh` 完成"构建 + 稀疏烧录 + 判读"（详见 `./30-构建-烧录-调试实战.md`）。

### 【背景知识】

> 💡 **什么是"烧录 / 下载口"？** 烧录就是把程序"刻"进芯片的不挥发存储器（Flash）。芯片通过一根串口线和电脑相连，"下载口"就是这根线在电脑上对应的串口号（Windows 叫 COM3，Linux 常叫 /dev/ttyUSBx）。

## 模块六：调试手段（J-Link + UART 控制台）

### 【理论】

写嵌入式程序，"能跑但不知道为啥卡住"是常态，所以需要调试手段。本项目两套：

1. **J-Link SWD**：硬件调试器，通过 **SWD** 接口连芯片（当前板级验证路线 `P0=SWCLK`、`P1=SWDIO`；`P20/P21` 为编译可用的备选），能单步、看寄存器、设断点。详细见 `docs/bk7258-t5ai/jlink-swd-debug-guide.md`。
2. **UART 控制台（console）**：芯片把运行日志通过串口打印出来，你用串口终端看。本项目 **console 走 UART1，波特率 460800，8N1**（8 数据位、无校验、1 停止位）。

### 【图解】

```
   电脑
   ├── J-Link ──SWD(P0/P1)──► BK7258   (硬调试: 断点/单步)
   └── 串口终端 ──UART1 460800 8N1──► BK7258 日志 (软观测: 看打印)
```

### 【实操步骤】

1. J-Link 连线：SWCLK→P0，SWDIO→P1（当前板级验证路线；具体接线见 `jlink-swd-debug-guide.md`）。
2. 打开串口终端，连到 console 对应的串口，参数设为 **460800 / 8 / N / 1**。
3. 上电或复位芯片，观察终端是否有 NuttX 启动日志输出。

### 【背景知识】

> 💡 **波特率 460800 8N1 是什么？** 串口收发双方要约定"每秒传多少比特"（波特率）以及数据帧格式。460800 是本项目约定的速率；8N1 表示"8 位数据、无校验位、1 位停止位"——双方参数必须一致否则会乱码。
