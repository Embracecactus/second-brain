# 板级初始化

> 目标：看懂 BK7258 板级初始化层——NuttX 上电后，平台服务、文件系统、Flash 存储是怎么一步步搭起来的。

## 本组导读

BK7258 是**双核**芯片：CP 核（通信处理器，管 RF/PHY/MAC）跑 NuttX，AP 核（应用处理器）是搭档。本组代码负责 NuttX 启动的**收尾阶段**：把 CP/AP 两世界间的桥梁和应用可见的设备/文件系统搭好。

```
BL1 → BL2(MCUboot) → CP 核 NuttX 内核启动
   │
   ├─ board_late_initialize()  ← bk7258_boot.c
   │     └─ bk7258_platform_initialize()  ← SDK/IPC/PM/PSRAM/AP 生命周期/WDT（核心）
   └─ NSH 起来后 board_app_initialize() ← bk7258_appinit.c
         └─ bk7258_bringup()  ← procfs/MTD/文件系统
```

**boot 负责"叫醒"，platform 负责"干重活"，appinit/bringup 负责"挂设备"**；其余四个是被调用的"工具人"：flash_guard 是 Flash 门卫，flash_mtd 是 NuttX 的 Flash 适配器，sdk_partition 是 SDK 分区翻译官，mac_storage 是 MAC 地址保险柜。

> 💡 高频词：**CP/AP**（CP 管无线、是主控；AP 是搭档，靠 **mbox 邮箱**跨核通信）；**SDK**（Beken 官方 armino SDK，封装寄存器操作）；**lower-half 下半层**（NuttX 驱动里"这块板特有的实现"）；**看门狗 WDT**（倒计时器，不"喂狗"就自动复位）；**XIP**（直接在 Flash 里取指执行）。
## 文件：bk7258_internal.h

**它干什么**：板级各层之间的"接口名片"，声明三个跨文件函数。
> 💡 像公司内部通讯录——只写名字和联系方式，不写怎么干活。
【核心结构】3 个函数声明：
```c
int bk7258_platform_initialize(void);
int bk7258_bringup(void);
#if !defined(CONFIG_BK7258_AP_CORE) && \
    (defined(CONFIG_BK7258_BT_IPC) || defined(CONFIG_BK7258_WIFI_VNET))
int bk7258_mac_storage_initialize(void);
#endif
```
【关键代码逐段讲解】`#if !defined(CONFIG_BK7258_AP_CORE)` 用编译开关区分"当前是 CP 还是 AP 核"。MAC 存储只属于 CP（只有 CP 有射频），AP 编译时就不声明。用宏裁剪代码是嵌入式最常见的技巧。

【流程/关系图】
```mermaid
flowchart LR     boot-->platform[bk7258_platform_initialize]; appinit-->bringup[bk7258_bringup]; platform-->mac[bk7258_mac_storage_initialize]
```
## 文件：bk7258_boot.c

**它干什么**：实现 NuttX 的"迟到初始化"入口 `board_late_initialize()`，叫响平台初始化第一声。
> 💡 为什么叫 late？NuttX 启动分两步：**early**（只够初始化串口/控制台）和 **late**（内核调度器就绪，可起线程、上锁了）。平台服务大多要等待/睡眠，必须放 late。
【核心结构】全文件只有一个函数：
```c
void board_late_initialize(void)
{
  int ret = bk7258_platform_initialize();
  if (ret < 0)
    {
      _err("bk7258: mandatory platform initialization failed: %d\n", ret);
    }
}
```
【关键代码逐段讲解】只调一个函数、接住返回值；失败只打日志**不 panic**——平台服务失败不至于立刻死机，先记下来能跑多远跑多远，方便日志定位。本函数返回 `void`，是 NuttX 框架固定接口，结果只能自己消化。

【流程/关系图】
```mermaid
flowchart LR    NX[NuttX 内核]-->LATE[board_late_initialize]-->PLAT[bk7258_platform_initialize]
```
## 文件：bk7258_appinit.c

**它干什么**：实现 `board_app_initialize()`，把应用侧服务注册转交给 `bk7258_bringup()`。
> 💡 只在 **NSH（NuttX 自带命令行 Shell）** 启用时才被调用；不开 NSH 就完全靠 late 阶段。
【核心结构】同样是"转发器"：
```c
int board_app_initialize(uintptr_t arg)
{
  (void)arg;
  return bk7258_bringup();
}
```
【关键代码逐段讲解】`uintptr_t arg` 是框架固定参数，用不上，`(void)arg` 是"我知道有你但不用你"，防编译器警告。与 boot 的分工：boot 管**强制性平台服务**（无论有没有 Shell），appinit 管**面向应用的设备**——所以平台初始化不放在这里，避免"不开 Shell 就什么都没有"。

【流程/关系图】
```mermaid
flowchart LR    NSH[NSH 启动]-->APP[board_app_initialize]-->BR[bk7258_bringup]
```
## 文件：bk7258_platform.c

**它干什么**：本组**绝对核心**，一次性完成所有强制性 CP/AP 平台服务初始化，顺序高度讲究。
> 💡 想象指挥双人接力：先给 CP 选手装备（SDK/IPC），再趁 AP 没醒时把它的专属用品（Wi-Fi/蓝牙端点、GPIO/PM 服务）提前摆到交接点，最后才"叫醒 AP"，再装安全绳（看门狗）。
【核心结构】`g_bk7258_platform_lock`（互斥锁）、`g_bk7258_platform_initialized`（幂等标记）、`bk7258_sdk_runtime_initialize()`（SDK 运行时，IPC 前提）、`bk7258_ap_control_initialize()`/`bk7258_ap_start()`（掌握并释放 AP）、`bk7258_psram_initialize()`（PSRAM 自检）、`bk7258_wdt_initialize()`（最后装看门狗）。
【关键代码逐段讲解】

**① 互斥锁 + 幂等（第 109-121 行）**——防"同时执行"和"重复执行"：
```c
  lockret = nxmutex_lock(&g_bk7258_platform_lock);
  ...
  if (g_bk7258_platform_initialized)
    {
      int saved_result = g_bk7258_platform_result;
      nxmutex_unlock(&g_bk7258_platform_lock);
      return saved_result;
    }
```
- `nxmutex_lock` 上锁：NuttX 的 **mutex（互斥锁）** 保证同一时刻只有一个线程进来，否则同时初始化 Flash/寄存器会乱套。
- `g_bk7258_platform_initialized` 是**幂等**（做一次=做一万次）。platform 可能被 boot 和 appinit 两条路都调到，第二次直接返回第一次的结果。

**② SDK 运行时是"地基"（第 137-146 行）**：
```c
#ifdef CONFIG_BK7258_SDK_IPC_RUNTIME
  apret = bk7258_sdk_runtime_initialize();
  ...
  if (apret < 0)
    _err("bk7258: SDK IPC runtime init failed: %d\n", apret);
#endif
```
后面所有服务都依赖 SDK 的 IPC 通道，所以它**必须第一个**初始化；每个后续服务都用 `if (apret >= 0)` 判断——前一步失败就跳过，避免在坏地基上盖楼。

**③ AP 生命周期：先发装备后叫醒（第 259-275 行）**：
```c
  static const struct bk7258_ap_image_desc_s ap_image =
    {
      .slot_start = BK7258_AP_FLASH_ADDR,
      .slot_end = BK7258_AP_FLASH_ADDR + BK7258_AP_FLASH_SIZE,
      .vector_addr = BK7258_AP_VECTOR_ADDR,
    };
  if (apret >= 0)
    apret = bk7258_ap_control_initialize(&ap_image);
```
- `ap_image` 描述 AP 固件放哪个 Flash 区间、**向量表**（CPU 复位后第一个查的内存表，存入口地址）在哪——相当于告诉 CP"搭档住哪栋楼、从哪个门进"。
- 文件里 Wi-Fi/蓝牙/GPIO/PM 初始化都在 AP 释放**之前**，注释说得很直白：冷启动的 AP 一旦打开会立刻去连端点，**CP 还没建好端点 AP 就卡死**。这是双核系统最容易踩的"时序坑"。

**④ PSRAM 自检（第 310-322 行节选）**：
```c
  psramret = bk7258_psram_initialize();
  (void)bk7258_psram_get_info(&psram);
  if (psramret < 0)
    syslog(LOG_ERR, "BPSR BOOT FAIL ... expected=%08lx actual=%08lx\n", ...);
  else
    syslog(LOG_INFO, "BPSR BOOT PASS id=%04lx config=%04lx capacity=%lu ...\n", ...);
```
失败打印详细诊断（芯片 ID、配置值、期望 vs 实际），一眼看出是颗粒不对还是配置不对。注释强调"别把它挪回 `__start()`"：工厂镜像走首次校准长路径，SDK 规定校准必须在 PSRAM 之前——真实踩坑总结出的纪律。

**⑤ 看门狗最后才上（第 382-400 行节选）**：
```c
#ifdef CONFIG_BK7258_WDT_FAULT_INJECTION
  result = bk7258_wdt_fault_validate();
#else
  result = bk7258_wdt_initialize();
#endif
```
为什么最后？AP 启动的某些自检可能**合法地**超过看门狗默认 8 秒周期，提前上狗会把"慢但正常"当成"卡死"而反复重启。

**⑥ 收尾（第 468-474 行）**：
```c
  g_bk7258_platform_result = apret < 0 ? apret : result;
  g_bk7258_platform_initialized = true;
  nxmutex_unlock(&g_bk7258_platform_lock);
  return g_bk7258_platform_result;
```
把最严重的错误存好、打"已完成"标记、解锁、返回。整个函数体现黄金法则：**上锁 → 幂等检查 → 按依赖顺序初始化 → 记住结果 → 解锁**。

【流程/关系图】
```mermaid
flowchart TB     ENTER-->LOCK[上锁+幂等]-->SDK[SDK IPC]-->SER[SARADC]-->PM[PM 时钟]-->TEMP[温度]-->MAC[MAC 绑定]-->WIFI[Wi-Fi 端点]-->BT[蓝牙端点]-->PSRAM[PSRAM 自检]-->AP[AP 控制]-->START[释放 AP]-->WDT[看门狗最后]-->OUT[记录结果返回]
```
## 文件：bk7258_bringup.c

**它干什么**：布置"应用橱窗"——挂 procfs、注册 MTD、挂载 LittleFS 文件系统。
> 💡 platform 是"给芯片用的"，bringup 是"给人（应用）用的"：酒店先完成水电基建（platform），再摆好大堂设施（bringup）。
【核心结构】`bk7258_fs_mount()`（MTD→块设备→文件系统）、`bk7258_flash_mtd_initialize()`（创建数据分区 MTD）、`bk7258_mcuboot_mtd_get()`（取 A/B 分区 MTD，仅 BL2）；常量 `/data` 与 `/dev/mtdblock0`。
【关键代码逐段讲解】

**① 先保地基再摆设施（第 84-88 行）**：
```c
  ret = bk7258_platform_initialize();
  if (ret < 0)
    return ret;
```
platform 是幂等的，这里再调不会重复干活，只保证"平台服务一定已就绪"。

**② procfs 注册顺序讲究（第 90-107 行）**：
```c
#if defined(CONFIG_FS_PROCFS) && defined(CONFIG_BK7258_DVFS_PROCFS)
  (void)bk7258_dvfs_procfs_register();
#endif
#if defined(CONFIG_FS_PROCFS) && defined(CONFIG_NSH_PROC_MOUNTPOINT)
  (void)mount(NULL, CONFIG_NSH_PROC_MOUNTPOINT, "procfs", 0, NULL);
#endif
```
**procfs** 是"伪文件系统"，`/proc` 下的文件是内核变量的投影，方便 `cat /proc/xxx` 看内核状态。注释强调**先注册后挂载**：NuttX procfs 挂载时会固化条目表，挂载后再加条目会和并发访问打架——"踩过坑"的注释最有价值。

**③ 文件系统搭建（第 48-65 行节选）**：
```c
  if (ftl_initialize(0, mtd) < 0)
    {
      _err("bk7258: failed to register LittleFS FTL block device\n");
      return;
    }
  mkdir(BK7258_FS_MOUNTPOINT, 0777);
  if (mount(BK7258_FS_BLOCKDEV, BK7258_FS_MOUNTPOINT, "littlefs", 0,
            "autoformat") < 0)
    { ... }
```
- **FTL**（闪存转换层）把 Flash"翻译"成可随机读写的块设备 `/dev/mtdblock0`；**LittleFS** 是专为小容量 Flash 设计的文件系统，`"autoformat"` 表示"没有就自动格式化"。
- 注意注释的克制：**正常启动绝不做存储校验**，防止每次开机写探针文件磨损 Flash——验证留给专门的测试应用。

【流程/关系图】
```mermaid
flowchart TB     B[bringup]-->P1[调 platform 保地基]; B-->DVFS[注册 /proc/dvfs]-->PROCFS[挂载 procfs]; B-->MTD[flash_mtd_initialize]; MTD-->LFS{开 LittleFS?}-->|是|MOUNT[FTL+挂 /data]; MTD-->MCU{MCUboot?}-->|是|SLOTS[注册 A/B 分区]
```
## 文件：bk7258_flash_guard.c

**它干什么**：给 CP 直接操作的原始 Flash 装了一把锁和一张权限表——同时只允许一个线程碰 Flash，且只准写自己名下的分区。
> 💡 Flash 是一间实验室，只有一台贵重仪器。这个文件是管理员：**进门要登记（加锁），只准做你申请的实验（分区权限），做完立刻离开（解锁）**。别人想插队？门口排队。
【核心结构】`g_bk7258_flash_guard`（互斥锁）、`g_bk7258_flash_guard_pid/owner/depth`（占门人/权限/嵌套深度）、`bk7258_flash_guard_lock/unlock()`（进门/出门）、`bk7258_flash_guard_write_authorized()`（地址写权限检查）。
【关键代码逐段讲解】

**① 写权限检查（第 79-87 行）**——写前先问管理员"我合法吗"：
```c
  owner = g_bk7258_flash_guard_owner;
  return !up_interrupt_context() &&
         g_bk7258_flash_guard_pid == nxsched_gettid() &&
         bk7258_flash_guard_range(owner, addr, size);
```
三个条件缺一不可：①**不在中断上下文**（中断里不能睡眠等锁）；②**持锁的人是我**；③**地址落在名下的分区范围**（防越界写坏别人的固件）。

**② 上锁与"同人免排队"（第 104-124 行节选）**：
```c
  if (g_bk7258_flash_guard_pid == nxsched_gettid() &&
      g_bk7258_flash_guard_owner == owner &&
      g_bk7258_flash_guard_depth != 0)
    {
      g_bk7258_flash_guard_depth++;
      __asm volatile ("dmb sy" ::: "memory");
      return OK;
    }
  if (write_access && owner == BK7258_FLASH_GUARD_MCUBOOT)
    return -EROFS;
  ...
  ret = nxmutex_timedlock(&g_bk7258_flash_guard, timeout_ms);
```
- **嵌套**：同线程已持锁再调 lock，深度 +1 直接放行（否则自己锁死自己），经典"可重入锁"。
- MCUboot 区要写 → 直接拒绝 `-EROFS`（只读）：A/B 固件分区只读，防误写刷坏系统。
- `nxmutex_timedlock` 支持超时等待；`dmb sy` 是 ARM **内存屏障**，让锁状态立即对其他核可见——多核与单核代码最本质的差别之一。

**③ 解锁与断言（第 140-157 行节选）**：
```c
void bk7258_flash_guard_unlock(void)
{
  DEBUGASSERT(g_bk7258_flash_guard_pid == nxsched_gettid());
  DEBUGASSERT(g_bk7258_flash_guard_depth != 0);
  if (g_bk7258_flash_guard_depth > 1)
    {
      g_bk7258_flash_guard_depth--;
      __asm volatile ("dmb sy" ::: "memory");
      return;
    }
  ...
  nxmutex_unlock(&g_bk7258_flash_guard);
}
```
`DEBUGASSERT` 是调试期断言：**不是本人来解锁、或没锁就解锁**，开发时直接触发异常，把配对错误扼杀在摇篮里。

【流程/关系图】
```mermaid
flowchart TB     A[lock]-->Q{同线程已持锁?}; Q-->|是|DEPTH[深度+1]; Q-->|否|MUTEX[互斥锁排队]-->REC[记录 pid/owner]; A-->WR[读写 Flash]-->UN[unlock]; UN-->DEP2{深度>1?}-->|是|DEC[深度-1]; DEP2-->|否|REL[彻底解锁]
```
## 文件：bk7258_flash_mtd.c

**它干什么**：把原始 Flash 包装成 NuttX 标准 **MTD 设备**，让上层统一读写；MCUboot 模式还额外导出两个 A/B 固件分区的只读 MTD。
> 💡 **MTD**（存储技术设备）是 Linux/NuttX 给"Flash 这类不能像磁盘一样覆盖写的存储"抽象出的标准接口。本文件是"SDK 的 Flash 函数 ↔ NuttX 标准接口"的**翻译官**，全程零寄存器访问，只调 SDK 的 `bk_flash_*`。
【核心结构】`struct bk7258_flash_mtd_s`（私有状态：基址/大小/是否 CRC/所属守卫）、`g_bk7258_data_mtd`（1 MiB 数据分区）、`g_bk7258_mcuboot_parent_mtd`（A/B 固件对合成的只读父分区）、`bk7258_flash_bread/bwrite/erase`（MTD 标准方法）。
【关键代码逐段讲解】

**① 关键背景：可执行 Flash 是"32+2"格式（第 166-171 行注释）**：
```c
/* The boot ROM/XIP controller exposes executable Flash as 32 data bytes
 * followed by two CRC16 bytes. ...
 */
```
固件区的每个 34 字节"包"里只有 32 字节真数据，后 2 字节是 CRC16 校验——CPU 在 Flash 上 **XIP** 直接取指执行，CRC 保证取到的指令没被改坏。而 NuttX 的 MCUboot 协议要求**连续字节流**，所以 `bk7258_flash_crc_read()` 边读边"剥壳"：读 34 字节包 → 验算 CRC → 把 32 字节真数据交给上层。

**② 块读：先查边界再拿锁（第 243-276 行节选）**：
```c
  if (state == NULL || startblock < 0 ||
      (size_t)startblock + nblocks > state->size / BK7258_FLASH_BLOCK_SIZE)
    return -EINVAL;
  if (bk7258_flash_mtd_lock(state, false) < 0)
    return -EINTR;
```
`startblock` 是**逻辑块号**，越界直接 `-EINVAL`——多核系统里谁都能调 Flash，边界必须自己守住。读前拿"读锁"（`write=false`）；读无特权，但**写**必须过守卫校验。

**③ 擦除/写：先解保护再动手（第 304-320 行节选）**：
```c
  bk_flash_set_protect_type(FLASH_PROTECT_NONE);
  for (block = 0; block < nblocks; block++)
    {
      uint32_t addr = state->base +
                      ((size_t)startblock + block) * BK7258_FLASH_BLOCK_SIZE;
      if (bk_flash_erase_sector(addr) != BK_OK)
        {
          bk_flash_set_protect_type(FLASH_UNPROTECT_LAST_BLOCK);
          bk7258_flash_mtd_unlock();
          return -EIO;
        }
    }
  bk_flash_set_protect_type(FLASH_UNPROTECT_LAST_BLOCK);
```
Flash 有硬件写保护（SR0 寄存器），写前 `FLASH_PROTECT_NONE` 解除，写后恢复为"只保护最后一块（引导区）"。**失败路径也必须恢复保护并解锁**——成功/失败路径对称，是正确性关键。

**④ 初始化：验明正身才开工（第 519-543 行节选）**：
```c
  if (bk_flash_driver_init() != BK_OK)
    return NULL;
  id = bk_flash_get_id() & 0x00ffffffu;
  if (id != BK7258_FLASH_ID_GD25WQ64E && id != BK7258_FLASH_ID_GD25Q64E && id != BK7258_FLASH_ID_W25Q64 && id != BK7258_FLASH_ID_TH25Q64)
    {
      ferr("ERROR: Unknown flash ID 0x%06" PRIx32 "\n", id);
      return NULL;
    }
```
先初始化 SDK 驱动，再读 JEDEC ID（Flash 的"身份证号"）。只接受 4 个已知型号，未知直接拒绝——防止"芯片换了、代码照旧"的诡异故障。

**⑤ MCUboot A/B 分区导出（第 547-570 行）**：
```c
  if (g_bk7258_mcuboot_slots[slot] == NULL)
    g_bk7258_mcuboot_slots[slot] =
      mtd_partition(&g_bk7258_mcuboot_parent_mtd.mtd,
                    (off_t)slot * BK7258_MCUBOOT_PAIR_BLOCKS,
                    BK7258_MCUBOOT_PAIR_BLOCKS);
```
`mtd_partition` 是 NuttX 标准"切片"工具：从父分区切出偏移和长度，得到主/备两个只读子分区，供 MCUboot BL2 做固件校验与升级。

【流程/关系图】
```mermaid
flowchart TB     INIT[initialize]-->DRV[bk_flash_driver_init]-->ID[JEDEC ID 校验]-->BIND[绑定 MTD 方法]-->DATA[数据区 MTD]; BIND-->MCU[MCUboot 父 MTD]-->PART[mtd_partition]-->P[primary/secondary]; DATA-->LFS[LittleFS /dev/mtdblock0]
```
## 文件：bk7258_sdk_partition.c

**它干什么**：用链接器 `--wrap` 技巧"狸猫换太子"——SDK 静态库里的分区表保持不变，但所有分区操作都改走**本项目自己的 CSV 分区布局**。
> 💡 SDK 是**预编译静态库**（二进制，改不了）。`--wrap` 是链接器钩子：代码里写 `bk_flash_partition_read(...)`，链接器就悄悄换成 `__wrap_bk_flash_partition_read(...)`——我们自己实现 `__wrap_*` 函数，就能"劫持"SDK 所有分区调用，而 SDK 库**原函数一行不用改**。
【核心结构】`struct bk7258_sdk_partition_s`（分区表项，与 SDK 二进制逐字节兼容）、`g_bk7258_sdk_partitions[]`（宏展开的分区表）、`bk7258_sdk_partition_write_allowed()`（写入资格判定）、`__wrap_bk_flash_partition_read/write/erase`（劫持后的读/写/擦除）。
【关键代码逐段讲解】

**① 分区表用宏自动生成（第 86-90 行）**：
```c
static const struct bk7258_sdk_partition_s
  g_bk7258_sdk_partitions[BK7258_SDK_PARTITIONS_TABLE_SIZE] =
{
  BK7258_SDK_PARTITION_FOREACH(BK7258_SDK_PARTITION_ENTRY)
};
```
`BK7258_SDK_PARTITION_FOREACH` 来自项目生成的 CSV 头文件，展开成一串宏，`BK7258_SDK_PARTITION_ENTRY` 再把每条变成 C 数组初始化语句。**改分区表 = 改 CSV 重新生成，不动 C 代码**。

**② 写权限判定（第 149-160 行）**：
```c
  if ((partition->options & BK7258_SDK_PARTITION_WRITE) == 0 ||
      (partition->options & BK7258_SDK_PARTITION_EXECUTE) != 0 ||
      bk7258_sdk_partition_guarded(partition))
    return BK_FAIL;
  return BK_OK;
```
三个拒绝条件：没写权限；是**可执行**的（固件区，写了就崩）；或受守卫保护（slot B 备用对 / LittleFS 数据区）。

**③ 劫持后的写（第 260-296 行，全文最核心）**：
```c
bk_err_t __wrap_bk_flash_partition_write(uint32_t partition,
                                         const uint8_t *buffer,
                                         uint32_t offset, uint32_t length)
{
  const struct bk7258_sdk_partition_s *info;
  bk_err_t ret;
  ...
  info = bk7258_sdk_partition_info(partition);
  if (info == NULL)
    return BK_ERR_FLASH_PARTITION_NOT_FOUND;
  if (!bk7258_sdk_partition_range(info, offset, length))
    return BK_ERR_FLASH_ADDR_OUT_OF_RANGE;
  ...
  ret = bk7258_sdk_partition_write_by_addr_allowed(info->start + offset,
                                                    length);
  if (ret != BK_OK)
    return ret;
  return bk_flash_write_bytes(info->start + offset, buffer, length);
}
```
教科书级"四步闸门"：**空指针 → 分区存在 → 越界 → 写权限**，全通过才调底层 `bk_flash_write_bytes`。注意权限检查里嵌套了 flash_guard：当前线程正拿着 `BK7258_FLASH_GUARD_DATA` 守卫就放行，否则走分区表自判——两层防线各有用途。

**④ 读要处理 32 字节对齐（第 234-254 行节选）**：
```c
  aligned_offset = offset & ~(BK7258_SDK_READ_ALIGNMENT - 1u);
  aligned_end = (offset + length + BK7258_SDK_READ_ALIGNMENT - 1u) &
                ~(BK7258_SDK_READ_ALIGNMENT - 1u);
  aligned_length = aligned_end - aligned_offset;
  aligned_buffer = (uint8_t *)bk7258_sdk_malloc(aligned_length);
```
SDK 底层读要求 **32 字节对齐**（Flash 按 32 字节页组织）。上层可能只想读 3 字节，所以 wrapper 先申请对齐缓冲区读整段，再从中"抠"出用户要的几字节——细节小，却是兼容任意上层调用的关键。

【流程/关系图】
```mermaid
flowchart LR     SDK[SDK 内部调用]-->|--wrap 劫持|W[__wrap_..._write]-->CHK{指针/分区/越界检查}-->|通过|PERM{写权限}-->GUARD{flash_guard 持锁?}; GUARD-->|是|GO[bk_flash_write_bytes]; GUARD-->|否|TABLE[查分区表权限]
```
## 文件：bk7258_mac_storage.c

**它干什么**：把蓝牙/Wi-Fi 的 MAC 地址读写需求，映射到项目自己的分区（SYS_RF/SYS_NET），注册成上层可用的存储回调。
> 💡 每个设备都有**出厂唯一的 MAC 地址**，存在 Flash 固定分区。SDK 只管"怎么读写"，本文件告诉它"写到哪个分区、写前怎么校验"。
【核心结构】`bk7258_mac_store_resolve()`（存储类型→分区）、`bk7258_mac_store_validate()`（校验分区起点/长度/偏移）、`bk7258_mac_store_read/write()`（真正的读/写）、`bk7258_mac_storage_initialize()`（注册回调）。
【关键代码逐段讲解】

**① 存储类型 → 分区映射（第 28-47 行节选）**：
```c
      case BK7258_BT_MAC_STORE_BACKUP:
        *partition = BK7258_SDK_PARTITION_SYS_RF;
        *expected_start = BK7258_SDK_SYS_RF_START;
        return OK;
      case BK7258_BT_MAC_STORE_NETWORK:
        *partition = BK7258_SDK_PARTITION_SYS_NET;
        *expected_start = BK7258_SDK_SYS_NET_START;
        return OK;
```
蓝牙 MAC 备份放 `SYS_RF`（射频区），网络 MAC 放 `SYS_NET`。validate 里核对 `info->start != expected_start`——**防 CSV 分区表改过之后旧代码拿旧地址写**，把 MAC 写进别处。

**② 网络 MAC 写要"整扇区事务"（第 104-112 行）**：
```c
  if (store == BK7258_BT_MAC_STORE_NETWORK)
    {
      /* Match SDK save_net_info(WIFI_MAC_ITEM): keep SYS_NET sector remainder */
      return bk_spec_flash_write_bytes(partition, buffer, length, offset) ==
             BK_OK ? OK : -EIO;
    }
```
Flash 擦除必须整扇区（4 KiB），改一个字节也得先擦整个扇区；只写新 MAC 会把扇区里其他校准项丢掉。所以网络 MAC 走 SDK 专用 `bk_spec_flash_write_bytes`（spec=special），**保留扇区其余部分再重写**，并与 SDK 原行为对齐。

【流程/关系图】
```mermaid
flowchart LR     REG[initialize]-->OPS[注册 read/write 回调]; OPS-->|写网络 MAC|SPEC[bk_spec_flash_write_bytes]; OPS-->|写备份 MAC|PW[bk_flash_partition_write]; OPS-->|读|PR[bk_flash_partition_read]
```
